\subsection{RQ6: the model, the log and the guardrail see different things}
\label{sec:views}

A detection rule never reads what the model read. It reads a view: the application's logged preview,
the fields that survive ingestion, the window a guardrail inspects. Three experiments measure where
these views part.

\paragraph{The logging gap (N1).} The demo application passes the first 2{,}000 characters of a tool
result to the model but logs only the first 1{,}000, a typical pair of defaults. With the L06
instruction placed after 1{,}500 characters of realistic shipment history, gpt-4.1-mini still followed
it in 7 of 10 runs and gpt-oss-120b in 3 of 7, while the instruction was absent from every logged
\texttt{tool\_result} in that cell (0 of 27 runs across the three models), so \llmd{021} could not fire. With the same instruction at offset 0
both models complied in 10 of 10 runs and the log contained it in all of them. Logging the last
1{,}000 characters as well (\texttt{tool\_result\_tail}) put the instruction back in the log in every
end-placed run; it does not help when the instruction sits in the middle of a long result. Beyond
2{,}000 characters the instruction is outside the model's view too, so those cells (8{,}000 to
70{,}000) measure the observers only. Both classifiers scored this payload below 0.01 at every offset,
including 0, so for this injection the classifier window did not matter: they did not recognise it
at all.

A rule for the gap itself, \llmd{022} (an untrusted tool result longer than its logged view followed
by a high-risk tool call in the same turn), caught 88\% of complied runs in a pre-registered
confirmation (N1b, 479 attack runs), but fired on 53\% of benign runs, and a refined version still on
32\%, failing the false-positive criterion; it is not part of the pack. The 1{,}000 and 2{,}000 character limits are this application's design; the experiment shows the
consequence of any such mismatch, not how common it is. The fix belongs in the application: the log
should let an auditor reconstruct what the model was given, for example its length, head, tail and a
hash of the rest, which avoids storing every credential or personal record that a tool returns.

\paragraph{The gap on frontier models (RQ5b).} On the Claude models with head-only logging and a
reworded instruction in the 1{,}000 to 2{,}000 gap, no model complied (0 of 30), and on Sonnet~5.5
and Opus~5.5 the provider refused every gap run (10 of 10 each) with an empty answer. With the
instruction beyond the 2{,}000 character window, nothing refused (0 of 30). So when the log did not
contain the instruction, the provider refusal was the only event any rule could use, and it appeared
only when the instruction string was part of the API request (not always then: at offset 0 Opus refused 7 of 10). On Haiku~4.5 the gap-placed
instruction left no trace of any kind. The pre-registered audit step that needed some gap runs to
comply, as evidence that the models read the instruction, failed; the refusal shows that the string
reached the API, not that the model attended to it.

\paragraph{The guardrail window (C2).} Microsoft documents that Azure AI Foundry guardrails moderate the
first 1{,}000 characters of text~\cite{foundry-guardrails}. On the author's own gpt-4.1-mini deployment with the default content
filter, 39 injection prompts that the filter blocks when sent alone were placed after benign filler.
In the user message the filter blocked 97\% of them at offset 0, 95\% at 500 and 85\% at 900,
and none at 1{,}100 or any larger offset (0 of 39 at each of six
offsets up to 20{,}000). In the tool-result message it blocked none at any offset, including 0. Every block was raised by the
jailbreak (user prompt attack) shield; no response carried an indirect-attack annotation, so the
opt-in shield for documents was not active in this default configuration. In
this deployment, then, the default filter blocked nothing that arrived as a tool result, which is
where indirect injection arrives, and nothing in user messages beyond the first 1{,}000 characters.
The 85\% at offset 900 missed the pre-registered 90\% threshold. This is one deployment, one model, one region and the default configuration; it is not a
statement about Azure AI Foundry in general. It is documented behaviour measured, not a
vulnerability; it means that a SOC cannot treat the absence of
guardrail events as evidence that no injection reached the model.
