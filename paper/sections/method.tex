\section{Methodology}
\label{sec:method}

We ask six research questions.
\textbf{RQ1}: when real models are attacked, how often do they comply, how often is harm achieved,
and what fraction of compromised runs does the pack detect?
\textbf{RQ2}: on public datasets of attacks and of real benign traffic, what recall and false-positive
rate do the content signatures achieve?
\textbf{RQ3}: how do they compare with, and combine with, open ML prompt-injection classifiers?
\textbf{RQ4}: how does detection hold up when the attack text is rewritten, and when an attacker
writes injections with the rule set in mind?
\textbf{RQ5}: what does a SIEM see of attacks on frontier models, which rarely complete them?
\textbf{RQ6}: where do the views of the model, the application log and the guardrail differ, and
what does an attacker gain from the difference?

\subsection{Protocol}
Results are held to a written evidence standard (\texttt{docs/research/evidence-standard.md}). RQ1 to
RQ3 and RQ4 Part A follow a study design committed before they ran but have no per-experiment
pre-registration. N1, N1b, C2, RQ4c, RQ5b, RQ5-C, RQ4d and RQ4e each have a pre-registration
committed to the public repository before the first run (by seconds to minutes; these are git commit
dates set by the author's machine, not external timestamps). The pre-registration of the first
frontier run (RQ5) was committed after its runs, so RQ5 is reported as exploratory. An observation made on
data already seen is not reported as a finding until a separately pre-registered confirmation on
fresh material (new repetitions, new wordings, held-out benign prompts) reproduces it. RQ4 Part A, RQ4c, RQ5 and RQ5b were reviewed
by an adversarial reviewer (an independent model instance instructed to find errors) before the
confirmatory runs; the whole paper, including RQ5-C, RQ4d and RQ4e, was reviewed the same way before
release. The errors found and the claims withdrawn are listed in Section~\ref{sec:process}.
Proportions carry Wilson 95\% intervals unless stated otherwise.

\subsection{Rule execution}
All rules run unchanged as KQL on the Kusto emulator (Kustainer, image pinned by digest). The only
modification is to widen a \texttt{trigger\_window} parameter that deduplicates alerts across
overlapping scheduled runs, because replayed data is not ``recent''. Events are loaded into a table
with the production schema (\texttt{LLMAppLogs\_CL}).

\subsection{RQ1 and RQ5: live attacks}
\paragraph{Models.} Twelve models with tool calling. Five open-weight models from five vendors, small
enough for an 8~GB consumer GPU (NVIDIA RTX~4060), served by Ollama~0.40.6 at default quantisation:
\input{generated/models.tex}. Three models deployed on Azure AI Foundry with the default content
filter: \input{generated/azure_models.tex}. Three Claude models through the Anthropic Messages API
(SDK 1.17.0): Haiku~4.5 with extended thinking (budget 1{,}024 tokens), Sonnet~5.5 and Opus~5.5 with
adaptive thinking and summarised display. RQ4d and RQ4e add Opus~4.8, configured like Opus~5.5.

\paragraph{Scenarios.} Ten attack scenarios in which only attacker inputs are fixed and the model's
behaviour is not scripted: a direct injection asking for the system prompt (L01); indirect injections
in two poisoned vendor documents, email exfiltration (L02) and an image beacon (L03); MCP tool
poisoning (L04), rug pull (L05) and runtime-response poisoning (L06) against a real MCP server; a
two-session memory poisoning (L07); agent configuration tampering (L08) and a reverse shell delivered
through pasted text (L09); and a base64-obfuscated injection (L10). The system prompt instructs the
assistant not to send email unless asked, and no high-risk tool requires approval, which is a common
and insecure default.

\paragraph{Oracles.} Each scenario has two independent oracles defined on side effects, never on the
rules: \emph{compliance} (the model took the attacker-directed step, for example it read the
restricted file the poisoned tool description asked for) and \emph{harm} (the attacker's goal was
achieved, for example restricted data reached the third-party tool). Oracles are unit-tested on
positive and negative traces. Each (model, scenario) pair runs 10 times on a fresh agent instance
(temperature 0.7 with fixed seeds where the API accepts it; the Claude runs use the API default).
Benign runs use 8 application questions and real prompts drawn from OASST2 and Dolly.

\paragraph{Frontier runs.} The first Claude run (repetitions r0 to r9) was exploratory; its analysis
was corrected after review (Section~\ref{sec:process}). The numbers reported for Claude come from a
confirmatory run (RQ5-C) with repetitions r10 to r19, none run before, and 50 held-out benign prompts
disjoint from every earlier benign run, with rule groups, metrics and decision criteria frozen in a
pre-registration committed before the first request.

\subsection{RQ2 and RQ3: public datasets and classifiers}
We assembled 112{,}894 items from 14 public datasets (16 dataset-surface sets, since OASST2 and Dolly
serve as both benign prompts and benign documents) (Table~\ref{tab:rq2-datasets}): labelled direct
injections and jailbreaks (deepset, Lakera Gandalf, neuralchemy, SPML, jackhhao, TrustAIRLab
in-the-wild), indirect injections embedded in documents (Microsoft's LLMail-Inject challenge
submissions~\cite{llmail}, BIPIA~\cite{bipia}, NVIDIA's agentic indirect injection set), poisoned MCP
tool descriptions from MCPTox~\cite{mcptox}, and benign material: real user prompts (WildChat-1M,
OASST2), crowd-written instructions and contexts (Dolly-15k), and real MCP tool descriptions
(MCP-Flow). Prompts become \texttt{prompt} events, documents become \texttt{retrieval} events and
tool results, and tool descriptions become \texttt{tool\_registry} events. WildChat is real traffic
that can itself contain attacks, so it is reported as an alert rate rather than a false-positive rate.
RQ2 intervals are percentile bootstrap (1{,}000 resamples).

Two open classifiers run with ONNX Runtime on CPU: ProtectAI's DeBERTa-v3 prompt-injection model
(v2)~\cite{protectai} and Meta's Llama Prompt Guard~2 (22M)~\cite{promptguard}, both at threshold 0.5.
ProtectAI's model card names jackhhao among its training data and lists eight unnamed MIT-licensed
sets, so we mark jackhhao as \emph{contaminated} and the MIT-licensed sets published before the model
(Lakera Gandalf, SPML, TrustAIRLab) as \emph{possibly contaminated}; headline numbers use the
remaining, clean datasets only.

\subsection{RQ4: rewritten and rule-aware attacks}
\emph{Part A} applies twelve fixed mutation operators once to each of 300 real attack prompts that the
rules detect at baseline: synonym substitution, homoglyphs, leetspeak, zero-width insertion, word
splitting and base64 wrapping; and paraphrase and translation into five languages by a local
Llama~3.1~8B (temperature~0, fixed seed). There is no feedback from the detectors, so this is a
non-adaptive lower bound on what an attacker achieves. \emph{RQ4c} gives the Claude models nine
injection framings written to avoid the phrases the content rules key on (for example a forged user
turn, a fake approval record, a fake error), delivered in an MCP tool reply that asks the agent to
email an internal file to an outside address. \emph{RQ4d} confirms an observation from RQ4c on fresh
framings (Section~\ref{sec:relay}). \emph{RQ4e} tries four injection families from the 2026
literature on Opus~5.5 and Opus~4.8 (Section~\ref{sec:opus}).

\subsection{RQ6: views}
N1 places the L06 instruction at a controlled character offset inside an MCP tool reply padded with
realistic shipment history (offsets 0, 1{,}500, 8{,}000, 40{,}000, 70{,}000; at the end or in the
middle) and records, for each run, whether the model acted and whether each observer saw the
instruction: the application log (first 1{,}000 characters, and optionally the last 1{,}000 as
\texttt{tool\_result\_tail}), the Sentinel table after ingestion, and the two classifiers. RQ5b repeats
the 1{,}000 to 2{,}000 character gap on the Claude models, first with tail logging on and then, in a
confirmation, with head-only logging. C2 measures the
inspection window of the Azure AI Foundry default content filter on the author's own deployment, in
the user channel and in the tool-result channel.
